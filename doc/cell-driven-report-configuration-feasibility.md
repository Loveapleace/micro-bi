# 单元格驱动报表配置的可行性评估

**后续决策（2026-10-20）：新cell模式不再要求选择全局报表布局及指标方向，发展为真正的模板格/父格/局部块展开。** 实施以[单元格驱动展开引擎设计](cell-driven-expansion-engine-design.md)为准；本文首期仅支持规范三表型的范围属于先前阶段记录，原面板仍保留。

评估日期：2026-10-19。源码观察基线：`e8eb3b4`。状态：可行性评估与建议范围，不是已实施方案或运行验收结果。

用户后续确认：保留当前面板方式，另增单元格设计，二者长期并行。完整实施规格见[双配置方式报表设计方案](C:/Users/And19/Desktop/web/micro-bi/doc/dual-mode-report-configuration-design.md)；以下评估不再表示用新增方式替换或降级原面板。

需求：从当前“字段探查 → 时间/分组/交叉维度面板 → 生成报表”，发展为在 Excel/Univer 画布中选中单元格进行基本配置，双击进入高级设置。正式展示仍使用 VTable，合并及格式继续遵守工作表配置。

## 1. 评估结论

**可行，适合发展为独立新增的配置方式，与原面板长期并行；首版应限制在现有引擎能表达的单区域明细、分组和双向交叉报表。**

单击、选择、属性面板和双击入口有现成的 SDK 接入基础；复杂度主要来自模板语义、父子作用域、动态展开和持久化，不是鼠标事件本身。若要支持帆软式任意父子格、独立过滤、嵌套区域与跨数据集关联，需要新增模板扩展与编译层，不能只把现有表单移动到单元格旁边。

不建议直接在已经展开的结果格中保存“字段 + A1 坐标”作为新方案。数据变化后，一个模板格可能生成多行多列，坐标无法稳定表达配置对象。

本次仅查阅官方资料和项目/依赖源码，未修改配置实现、运行交互原型或重跑已有整改用例；下面的可行性等级属于工程判断。

## 2. 帆软官方方式可以借鉴什么

参照 FineReport 11.0 官方帮助，未把其他帆软产品的功能混作 FineReport 能力。

| 官方机制 | 对本项目的启示 |
| --- | --- |
| 选中数据列单元格后在右侧配置；双击可打开数据列属性对话框 | 单击使用固定属性面板，避免弹窗阻断选区；双击提供更完整设置 |
| 数据列属性包括字段、父格、数据处理与扩展方向 | 单元格应绑定结构化规则，不仅保存显示文字 |
| 数据显示方式包含列表、分组、汇总 | 明确明细、维度和指标的业务含义，不能仅按字段物理类型猜测 |
| 单元格扩展与父格关系控制报表生成 | “父格”是数据上下文与扩展关系，不等于合并区域或相邻位置 |
| 交叉报表组合横向与纵向扩展 | 行成员与列成员共同限定度量格的数据范围 |

上述交互依据：[数据列属性](https://help.fanruan.com/finereport/doc-view-1232.html)；数据处理依据：[数据显示方式](https://help.fanruan.com/finereport/doc-view-151.html)；扩展与层级依据：[扩展属性简介](https://help.fanruan.com/finereport/doc-view-215.html)、[父子格设置](https://help.fanruan.com/finereport/doc-view-141.html)；二维实例依据：[交叉报表](https://help.fanruan.com/finereport/doc-view-2107.html)。

需要区别：官方说明是双击打开属性对话框，其中可以进入高级设置；“双击直接打开高级页”是我们拟采用的产品规则，不能说它就是帆软所有单元格的默认行为。

## 3. 当前架构能复用什么、缺少什么

| 当前代码 | 可复用基础 | 与新方式的差距 |
| --- | --- | --- |
| `src/engine/profiler.ts`、`DynamicDataConfigPanel.tsx` | 字段类型探查、用户纠偏、样本与标题 | 保留为字段选择器和推荐规则的依据，不应移除 |
| `src/core/datasetRegistry.ts` | 注册数据集、异步解析、缓存 | 数据源选择仍需要；跨数据源关系没有因此自动具备 |
| `src/engine/types.ts`、`pipeline.ts` | 明细/聚合、时间桶、行列维度、计算列 | 当前 DSL 是区域级配置，不能完整表达任意格的独立父格和过滤 |
| `src/report/buildBiGrid.ts`、两个 projector | 生成分组与双向交叉矩阵 | 当前是先配置分析，再生成结果；需要在前面补模板编译过程 |
| `src/univer/ReportConfigPanel.tsx` | 现有主配置入口、保存、快照与预览组合 | 当前主要处理 `analyses[0]`，不是任意单元格模板设计器 |
| `src/report/types.ts` 的 ReportBinding | 结果格的成员路径、指标身份、工作表位置 | 缺少稳定模板格定义，以及一个模板格到多个结果实例的对应关系 |
| `compileReport.ts`、`ReportTableView` | 发布模型与 VTable 展示路径 | 应继续保留；展示端不用承担新的查询/展开语义 |

字段类型检测仍有价值，但定位改变：它推荐时间粒度、默认操作与格式，而不是替用户决定业务角色。数值型设备编号可以作为分组，时间可以作为明细列，文本也可以参与计数；实际角色由单元格配置决定。

## 4. 单击和双击的交互评估

建议在“报表设计”状态采用用户要求的方式：

| 操作 | 建议行为 |
| --- | --- |
| 单击/键盘选中 | 更新右侧基本属性：数据集、字段、内容类型、列表/分组/汇总、时间粒度、扩展方式和显示名称 |
| 双击 | 打开该模板格的高级属性，优先展示高级页；普通选中面板不弹窗抢焦点 |
| F2、公式栏或明确的内容编辑入口 | 输入静态文字、工作表公式与允许的人工值，保留 Excel 内容编辑能力 |
| 右侧“高级设置”按钮 | 提供双击之外的入口，兼顾键盘、触屏及可发现性 |
| 选择多个格/合并格 | 先明确主格和作用范围；多选仅批量修改兼容属性，不默默替所有格重绑字段 |

双击原本会启动 Excel 内容编辑，不能同时打开高级弹窗和原生编辑器。若提供独立“内容编辑”模式，双击可恢复原生行为；模式与焦点策略应清楚显示。若不增加模式，建议仅数据模板格接管双击，普通文本/公式格仍保留内容编辑，并通过按钮进入高级设置。这两种交互都可行，首版应固定一种，不能在同一格中随机竞争。

本地 Univer 1.0.4 声明提供 `SelectionChanged`、`CellClicked`、`BeforeSheetEditStart`；后者带行列、`eventType` 和可取消标记。依赖源码中双击通过 `DeviceInputEventType.Dblclick` 进入编辑路径，因此存在在设计态拦截双击编辑的实现基础。

这里没有确认一个公开的 `CellDoubleClicked` 事件，不能直接按该名称开发，也不能依赖 Canvas 中并不存在的 DOM 单元格。需用真实 SDK 做最小原型验证：只拦截目标工作簿、目标模式下的双击，F2/键入不被误拦截，滚动、缩放、冻结和合并格的坐标正确，监听器可释放。

高级设置的完整目标可包含父格、过滤、排序、空值、总计/小计、业务表达式、局部公式和动态样式作用域。首版仅启用实际有编译与执行能力的项目；不能先开放任意过滤/父格配置，再静默忽略。

## 5. 明细、分组与交叉如何表达

| 报表形式 | 单元格模板的表达 | 当前引擎复用程度 |
| --- | --- | --- |
| 明细表 | 一组字段格共享同一条记录的重复区域，向下实例化，按主键对齐 | 高；不能让每列分别扩展后形成笛卡尔积 |
| 分组报表 | 维度格声明分组层级，指标格在父级数据范围中求汇总 | 高；自由位置父子关系需要补充模型 |
| 双向交叉 | 行维度向下、列维度向右，指标格在两者交集中计算 | 高；可先映射现有双轴配置 |
| 自由/嵌套报表 | 多个扩展块、独立父格与局部数据范围组合 | 当前没有完整编译层，需要新增 |
| 跨数据集交叉 | 依据明确关联键生成共同上下文 | 不能仅靠空间相邻推断关系，后续单独设计 |

以“车间 × 月份产量”为例，以下是建议的模板定义，不是当前已经实现的界面：

| 模板格 | 绑定 | 行为 | 数据上下文 |
| --- | --- | --- | --- |
| A2 | workshop | 分组，向下展开 | 当前数据集的车间集合 |
| B1 | plan_start_time | 按月分组，向右展开 | 当前数据集的月份集合 |
| B2 | output_qty | SUM，不新建独立扩展轴，随交叉区域生成实例 | 行父格 A2 + 列父格 B1 的数据交集 |

该受约束模板可以归一化成现有 `categories`、`columnTimeBucket`、`columns`，继续交给当前矩阵和聚合引擎执行。指标横向/纵向排列作为区域布局属性保存，不只靠用户把字段放在某个坐标来猜测。

对于多级车间/产线与月份/产品交叉，需要完整父路径；同名产线不能跨车间混算。AVG、COUNT、比例与总计仍按当前事实切片计算，不能根据屏幕上已经汇总的值再次平均或相加。

## 6. 必须增加的模板层

建议保持当前展示架构，在计算前增加模板解释层：

```mermaid
flowchart LR
  A[数据集与字段元信息] --> B[单元格模板定义]
  U[Univer 选区与属性编辑] --> B
  B --> C[区域和依赖校验]
  C --> D[归一化分析计划]
  D --> E[现有聚合与矩阵引擎]
  E --> F[展开实例与语义绑定]
  F --> P[配置预览与发布编译]
  P --> V[VTable 展示]
```

至少区分三层对象：

1. **模板格**：稳定 templateCellId、内容来源、datasetId/fieldId、操作、时间桶、扩展角色、父格/重复区域、布局及规则。A2 是当前位置，不是唯一身份。
2. **展开实例**：templateCellId + 明细主键或完整行列成员路径 + 指标/角色，映射到本次物理坐标。排序和增删成员后重新定位。
3. **发布单元格**：已经计算好的值、显示文本、格式和最终合并，继续由 VTable 消费。

ReportBinding 目前适合描述第二层的一部分，需要增加它与第一层的关联。只保存 Univer 快照或格内显示的字段名，无法完整恢复查询、父格、扩展和动态规则。

旧面板与新方式长期并存，各报表只有一份明确模式的可编辑源，通过适配器派生共用分析计划；不能让两种方式分别维护同一报表的两份可互相覆盖配置。转换通过显式复制和可表达性校验完成，不能在保存时降级丢弃当前 DSL 表达不了的自由规则。

## 7. 设计模板与预览结果需要区分

设计视图展示少量模板格，例如字段标记、汇总表达式和扩展指示；预览视图展示真正的车间、月份和数值。它们是同一份配置的两种视图，不是两份独立编辑来源。

在结果格上编辑时必须明确作用域：

- 修改模板，影响该模板格生成的全部实例。
- 修改某个业务成员/月份切片的格式或覆盖，仅影响匹配实例。
- 修改自由文本或自由布局块。

不能点到“车间A、十月”就默认改成整个产量指标，也不能把对该格的局部编辑存成固定 B5。预览仍可保留现有格式、备注、局部公式和人工覆盖能力，但这些编辑需要映射到明确的模板规则或实例覆盖。

字段绑定定义、普通字面值、业务计算表达式与 Excel 工作表公式也应分开。直接敲入一个数字表示内容编辑，不等同于重新绑定数据字段。

## 8. 主要风险与处理边界

| 风险 | 评估及必要控制 |
| --- | --- |
| 原生双击编辑与高级配置竞争 | 有 SDK 接入基础，需按模式/格类型路由并验证焦点、单次触发与输入提交 |
| 父格循环、失效引用与未知范围 | 父格/依赖按稳定 ID 建图，校验循环、缺失、跨区域和跨数据集关系 |
| 明细字段错行或重复聚合 | 同一重复区域共享记录身份，指标按父级事实范围计算，不独立展开每列 |
| 数据变化后配置错位 | 模板与实例分层，语义 ID、版本戳、重基及冲突处理沿用动态模板要求 |
| 任意父格导致布局冲突 | 需要扩展带/区域占用与排版算法；无法放置时有明确诊断，不覆盖手工块 |
| 多数据集自动相乘 | 首版每个分析区域限定一个数据集；跨源必须先定义关联键、基数和汇总口径 |
| 每格独立取数或扫描全量事实 | 按分析计划、数据版本和作用域合并计算，共享索引与聚合缓存；限制展开规模 |
| 双配置来源与撤销不一致 | 一次绑定编辑将模板、工作表表现和实例绑定作为同一事务；旧面板只作同模型投影 |
| 合并行为违反已确定口径 | 父格负责数据范围，合并属于模板版式；保留合并/取消意图，VTable 不按相邻同值补合并 |

Univer 当前接入承担画布、单元格编辑和工作表计算，不会自行解释项目的数据集父格和 BI 扩展定义。这一解释过程必须由项目的模板编译层实现。

首版不建议直接支持任意跨源父格、无限嵌套扩展、所有 Excel 函数和任意自由版式。它们不是不可做，而是会从“新配置入口”发展成完整的报表生成引擎。

## 9. 建议采用的范围

| 层次 | 建议范围 | 工程判断 |
| --- | --- | --- |
| 最小原型 | 选格显示侧栏，设计态双击高级，F2/公式栏编辑，一个车间×月份交叉模板 | 可行性高，先验证 SDK 交互与模型串联 |
| 第一版 | 同数据集、受约束重复区域，明细/分组/双轴，多指标方向，保存重开及动态刷新 | 建议作为正式目标，可复用现有引擎 |
| 后续扩展 | 任意父格、区域级/单格独立过滤、多个自由扩展块及复杂局部公式 | 需要模板依赖与布局编译器，不应伪装成纯 UI 改造 |
| 更后续 | 跨数据集关联、深层嵌套、完整文件互通和更广公式覆盖 | 独立评估执行策略、规模与能力范围 |

原有字段/维度面板作为完整配置方式保留，既有入口/API及编辑能力不减少；另增单元格设计。可额外提供“复制为单元格模板”，但不把旧面板降级为创建向导。两种源通过适配器复用计算和发布，完整约束见双配置方案。

实现排序建议为：模板/实例身份协议 → 单格属性与编辑冲突原型 → 受约束明细/分组/交叉编译 → 保存和动态重编译 → 再开放自由扩展。现有保存、动态刷新和合并一致性的整改，应复用和收敛，而不是引入另一条独立展示链路。

## 10. 最小原型的通过标准

以下仅为建议验证门槛，尚未执行：

1. 单击和键盘移动只刷新侧栏，不误改字段、不弹窗阻断双击；合并格定位到正确模板主格。
2. 设计态双击只打开一次高级设置，原生编辑器不同时出现；F2、公式栏、Esc 和关闭弹窗后的焦点正确。
3. 用三个模板格生成车间×月份 SUM 交叉结果，再扩展为多级分组与两种指标排列，逐格对照现有引擎。
4. 明细两列都跟随同一条事实记录，重复值不被去重，记录排序后仍按主键定位。
5. 增删事实、重排成员和增删月份后，模板绑定、实例覆盖、局部格式及公式作用域正确。
6. 模板编辑与单个实例编辑可以区分；取消草稿不影响正式报表，保存重开能恢复语义配置。
7. 合并/取消及之后的数据变化均遵守工作表规则，正式 VTable 不自行重分组或合并。
8. 父格循环、跨源未定义关系、主键重复和布局碰撞有明确诊断，不生成似是而非的数据。
9. 从原主配置入口保存，在原卡片 VTable 展示；展示态无需创建 Univer，不绕行独立演示页。
10. 记录不同数据规模与双轴基数下的编译、编辑和首屏成本，再确定展开预算，不预先承诺任意规模。

**采用建议：值得做。先把单元格设计作为现有分析能力的新表达，再逐步补充自由模板能力；不要将完整帆软式扩展模型当作一次属性面板替换。**
